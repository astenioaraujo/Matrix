# Matrix — Módulo Financeiro / Saldos

Contexto de projeto para o Claude Code. Para a especificação funcional completa (regras de negócio, mockups, decisões e histórico de por que cada coisa é do jeito que é), ver `docs/spec_saldos_matrix.md` — este arquivo é só o resumo operacional.

## O que é

Matrix é um sistema de análise de dados para uma rede de postos de combustível, multi-tenant (`cod_empresa`). Este trabalho é sobre o **Módulo Financeiro**, especificamente a funcionalidade **Saldos** (conciliação diária banco × sistema por filial), que deve ser o primeiro item do menu do Financeiro, antes de Fluxo de Caixa, Fluxo de Caixa Projetado, Empréstimos e Financiamentos, e Cadastros.

- Empresa em desenvolvimento: `cod_empresa = 'EMP010'`
- Banco: PostgreSQL via Supabase
- Autenticação: **custom**, não é Supabase Auth — tabela própria `usuarios` com `senha_hash`. Não existe `auth.uid()`.
- Controle de acesso: `usuarios_empresas` (empresa) + `usuarios_filiais` (filial) + `usuarios_permissoes` (ação/tela, ligada a `permissoes_catalogo`) — tudo checado na API, não em RLS por linha.
- RLS nas tabelas novas: habilitado só para bloquear acesso direto via chave anônima; a API usa a **service role key**.

## Convenções do schema (extraídas do banco real, seguir sempre)

- PK: `id_<entidade>` inteiro, `GENERATED BY DEFAULT AS IDENTITY`
- Toda tabela carrega `cod_empresa character varying` (multi-tenant)
- Filial é referenciada por `(cod_empresa, cod_filial)` — **nunca** por um `filiais.id` interno
- Área é referenciada por `id_area integer` (FK para `areas.id_area`)
- Status/tipo: `character varying` livre, não enum do Postgres
- Auditoria: `criado_em` / `atualizado_em` (`timestamp without time zone`, default `now()`)
- `ordem integer default 10`
- Nada de subtotal/total/diferença/variação como coluna — sempre calculado na consulta (via `SUM`/`LAG`), nunca persistido

## Tabelas já criadas (ver `migrations/criar_tabelas_saldos.sql`)

`contas_bancarias`, `indicadores_recebiveis`, `competencia_mes`, `saldos_bancarios`, `saldos_recebiveis`, `valores_informados`.

Pontos importantes:
- `contas_bancarias` e `indicadores_recebiveis` são cadastros **por empresa**, não por área — todas as áreas compartilham o mesmo conjunto; uma filial que não usa uma conta/indicador simplesmente lança zero.
- `saldos_recebiveis.id_indicador_recebivel` e `saldos_bancarios.id_conta_bancaria` são FK para cadastro, **não** valores fixos em código — o preenchimento diário é manual, e o cadastro é o que define as linhas mostradas na tela.
- Variação dia a dia é calculada automaticamente para qualquer conta/indicador cadastrado — nunca depende de lista fixa. **Não é mais via `LAG()` do SQL** (ver bug corrigido em 2026-07-03 abaixo) — é calculada em Python, comparando o valor de hoje com o de ontem, ambos já com default 0 quando não há lançamento.

## Acesso por área (2026-07-03)

Problema real: cada área tem seu próprio responsável pelo lançamento (ex.: Thalyta só pode mexer na Área I, Carol só na Área II). O controle de filial genérico (`usuarios_filiais`, usado por outros módulos do sistema) foi considerado **insuficiente/desacoplado demais** para isso — decidiu-se por um controle **por área, específico do módulo Saldos**:

- Tabela nova `usuarios_areas_saldos` (`cod_empresa`, `id_usuario`, `id_area`, `ativo`) — `migrations/criar_tabela_usuarios_areas_saldos.sql`, já rodada no banco.
- Regra: **só o acesso à área já basta** — não depende de `usuarios_filiais` para nada dentro de Saldos. Quem tem a área liberada aqui vê/lança em **todas** as filiais daquela área automaticamente.
- Superusuário sempre vê tudo (bypass, como no resto do sistema). Quem não é superusuário e não tem nenhuma área liberada não vê nenhuma área no seletor e recebe 404 se tentar consultar via API diretamente.
- Gerenciado na aba "Acesso por Área" de `cadastro_saldos.html`, atrás da mesma permissão `CADASTRO_CONTAS_BANCARIAS` (decisão explícita do cliente — não é exclusivo de superusuário, mesma trava das outras abas de cadastro).
- Endpoints: `GET/POST /api/usuarios-areas-saldos`, `DELETE /api/usuarios-areas-saldos/<id>`.
- Funções-chave em `routes/financeiro_routes.py`: `areas_permitidas_usuario()`, `filiais_permitidas_usuario()` (usada por `GET /api/saldos` e pela tela), `cod_filiais_permitidas_lancamento()` (usada pelos 3 PUTs de lançamento — resolve filiais a partir das áreas permitidas via `areas_filiais`, não mais via `usuario_filiais_ativas`).
- **Cuidado ao reusar `areas_permitidas_usuario`**: ela é chamada tanto com `RealDictCursor` quanto com cursor comum dependendo do endpoint — o código já trata os dois casos (`isinstance(linhas[0], dict)`), mas qualquer nova função parecida que misture os dois tipos de cursor precisa do mesmo cuidado (já caiu em `KeyError: 0` uma vez por causa disso).

## Bug corrigido: variação zerada quando falta lançamento no dia (2026-07-03)

Achado pelo cliente comparando duas áreas na tela: numa área a variação aparecia certa pra todas as filiais, na outra só pra uma. Causa: a variação era calculada via `LAG(saldo_banco) OVER (PARTITION BY cod_filial, id_conta_bancaria ORDER BY data)` **em cima das linhas existentes em `saldos_bancarios`/`saldos_recebiveis`** — se uma filial não tem lançamento num dia (nenhuma linha na tabela, não é uma linha com valor 0), o `LAG` simplesmente pula esse dia pra aquela filial, e o código em Python (`routes/financeiro_routes.py`, `montar_bloco_dia`) tratava a ausência de variação como `0.0`, escondendo uma variação real (o saldo "caiu" pra zero por falta de lançamento, mas isso não aparecia).

Corrigido: `montar_bloco_dia` agora recebe também as linhas do **dia anterior** (`linhas_bancarias_anterior`/`linhas_recebiveis_anterior`) e calcula `variação = valor_hoje − valor_ontem` inteiramente em Python, onde os dois lados já usam o mesmo default de `0.0` quando não há lançamento — consistente com o resto do sistema. O SQL não usa mais `LAG` pra isso, só busca os valores brutos.
